# Snapshots

Reth publishes modular node snapshots at
[snapshots.reth.rs](https://snapshots.reth.rs). The snapshot UI lets you choose
minimal, full, or archive components and gives you the matching `reth download`
command.

Use snapshots when you want to avoid syncing from genesis. `reth download`
extracts the selected components into your Reth data directory. It also writes
`reth.toml` for the selected components if the file does not already exist;
after extraction, start `reth node` normally.

## Latest minimal snapshot

For the default minimal component set:

```bash
reth download -y

reth node
```

## Snapshot sizes

Snapshot download sizes are compressed and change with the selected profile,
selected components, and latest published block. The
[snapshots.reth.rs](https://snapshots.reth.rs) UI shows the estimated download
size for the current selection.

You can also list snapshot sizes from the CLI:

```bash
reth download --list
```

## Choose a profile

```bash
# Smallest built-in profile
reth download --minimal

# Full-node profile
reth download --full

# Archive profile
reth download --archive
```

## Custom components

Use the website or `reth download` flags to include specific components, such
as transaction files, receipts, state history, senders, or RocksDB indices:

```bash
reth download \
    --with-txs-distance 100000 \
    --with-receipts-distance 100000 \
    -y
```

Transaction ranges download whole static files. For example, if a selected file
starts at block 10, `--with-txs-since 13` restores bodies from block 10. The
Bodies checkpoint records the block before the continuous range through the
snapshot tip, or a later boundary inherited from the source database.

`--with-state-history-since N` configures the node to retain state history
from block `N` onward. If `N` is above the snapshot height, the download skips
changeset archives and writes that future boundary to the generated `reth.toml`.

Legacy snapshots with changesets and history indices in MDBX carry that history
in the state archive. This includes v1.10 snapshots with static-file receipts,
and snapshots with static-file senders when the download omits senders.
After all archives are verified, the downloader checks the storage layout
before updating checkpoints. It reports any known legacy backend setting that
is incompatible with the selected download.

A v1 restore preserves the original changeset and index checkpoints, including
the mode needed to resume an interrupted prune. An explicit state-history
selection sets future retention when the downloader creates `reth.toml`.
On a retry, the downloader preserves the existing `reth.toml` and uses the current
download selection for any prune checkpoints it writes.

When `reth db migrate-v2` moves history from an older restore, it copies surviving
changesets even below the recorded prune checkpoint. A block can be partially
pruned, so historical queries keep the original read boundary.
