# Experimental EIP-8288 dependency proofs

This branch implements the leanSPHINCS dependency path on top of Bogota frame transactions. It is an opt-in devnet profile, not a finalized Ethereum consensus configuration. Enable it with a numeric `eip8288Time` in genesis `config`, together with the existing Bogota activation. Without that field, dependency frames and proof-bearing headers remain disabled.

## Cryptographic profile

The profile pins leanVM to `84780fb42667bc288c0e567c125b7e10479fb568`. It uses that revision's leanSPHINCS parameters, serialized signatures, native aggregate proof format, fixed aggregation bytecode, transcript domain and experimental prover. Native verification uses the same protocol as the reference prover. Building the backend requires Rust 1.97.1.

The pinned leanSPHINCS scheme uses Keccak-256 truncated to 16 bytes, WOTS+C with 2-bit chunks, 64 chains and target sum 128, a three-layer hypertree with bottom-first heights `[8, 8, 10]`, and 24 FORS trees of height 10. Messages and public keys are 32 bytes; signatures are 7,740 bytes. Aggregate proofs use native code-rate parameter `log_inv_rate = 1`. The upstream revision fixes the remaining address encodings, domain tags, program construction and deferred bytecode checks.

The header dependency digest is Keccak-256 of the concatenated `message_hash || public_key` pairs in the EIP's sorted, deduplicated dependency order. A leanSPHINCS public key is `PK.seed || PK.root`. Zero hashes in transaction frames are resolved to the canonical signing hash without changing the signed frame bytes.

The native leanVM statement sorts `(public_key, message_hash)` claims and binds additional fixed program, scheme-list and deferred-evaluation fields. The adapter reconstructs exactly those native claims from the independently reconstructed block dependencies and verifies them with the pinned program. This preserves exact dependency coverage, but differs from the draft's abstract two-public-input presentation. The draft still leaves `DEPS_HASH` and `AGGREGATED_VK` unspecified; this profile does not claim to finalize them.

A verified aggregate whose dependency set already matches the requested block set is reused byte for byte. Removing dependencies invokes recursive pruning; adding uncovered dependencies invokes aggregation with their witnesses. Proving throughput and slot-time compatibility remain experimental; operators must budget for the pinned prover's latency.

## Limits and policy extensions

Direct wrappers retain the draft limit of 16 distinct leanSPHINCS dependencies. Recursive wrappers are instead bounded at 16,384 dependencies, with aggregate proofs limited to 1 MiB. This deliberately resolves the draft's conflict between its 16-dependency recursive-wrapper limit and its requirement to aggregate an entire active pool. Witness limits are checked before cryptographic work, and the ordinary transaction and block gas limits continue to apply.

Dependency declarations may precede the existing account validation prefix, following any canonical expiry and recent-root frames. They preserve their actual indexes and contribute their declared execution budgets. They do not replace account authorization or payment approval. Pool admission checks the current EVM activation before verifying evidence for any transaction origin, including after a head rollback. The public-pool per-transaction limit counts distinct resolved claims; execution and intrinsic gas charge every declaration.

## Ownership and lifecycle

Alloy EIPs owns declaration and header-entry types. Alloy consensus owns structural validation, canonical dependency extraction and transaction gas calculations. evm2 implements non-EVM dependency-frame execution and receipts behind explicit activation. Reth verifies evidence before pool admission, retains immutable evidence with its consuming transactions, invokes the prover while building a payload and independently verifies exact block coverage during import. Removing a transaction removes its reference to evidence; a dependency shared with another retained transaction remains covered. Reorg reinsertion attaches the old canonical block's aggregate proof as shared evidence. Pool memory pressure accounting conservatively charges retained evidence to every consuming transaction.

The prover is run from blocking work. Ordinary transactions and pre-activation blocks neither initialize leanVM nor allocate proof buffers. Proof-bearing header data is boxed so historical headers carry only an optional pointer. No raw signature is added to the canonical transaction or block body.

## Wrapper transport

`eth_sendDependencyWrapper` accepts a single hex-encoded RLP byte string and returns transaction hashes. The bytes encode `[transactions, mode, [dependencies, witnesses_or_proof]]`. Each transaction entry is either its canonical EIP-2718 encoding or a 32-byte transaction hash already present in the receiving pool. Each dependency uses an RLP `[scheme, resolved_message_hash, public_key]` entry, in canonical order. Mode zero uses a list of raw signatures in that order; mode one uses a serialized native aggregate proof byte string. The whole wrapper is limited to 2 MiB.

Admission resolves every hash, reconstructs the exact union of dependencies, and verifies evidence before submitting any transaction to the ordinary pool validator. Pool changes during submission can still cause partial admission; this RPC is not an atomic transaction batch. A dependency frame does not authorize an account by itself. Account validation still runs through the existing EIP-8141 machinery. Frame transactions containing blob commitments require their blob sidecars through the existing pool path; the experimental wrapper has no blob-sidecar encoding.

Peers negotiate the experimental `eip8288/1` RLPx capability. Message zero contains wrapper bytes after its one-byte message ID. Message one has no body and requests a full current snapshot after an unresolved transaction hash. Full transaction bytes are sent before hash references are used for that peer. Recovery replaces the incomplete snapshot; missing transactions and wrappers are not accumulated in an unbounded retry table.

The aggregation worker checks once per second, keeps one proving job in flight, and reuses the last proof when the transaction set is unchanged. It recursively includes previous evidence and discards claims no longer needed by the selected transactions. Payload construction can reuse one bounded aggregate held by its pool, pruning it to the exact included dependencies; claims already covered by children do not repeat raw signature verification inside the proof. The gossip worker does not start proving without subscribed peers. RPC and peer verification share two blocking-job permits; event and per-peer queues hold at most 16 and 2 messages respectively, with at most 1,024 peer entries. Peer transaction-knowledge sets are immutable and shared across a snapshot. Failed or overloaded peer submissions are retried by subsequent snapshots.

Finite wire and proving budgets mean this implementation forwards a bounded pending-pool snapshot rather than promising to include an arbitrarily large active pool every second. It examines at most 16,384 pending transactions and reserves 1 MiB for proof bytes within the wrapper budget. Local block construction reconstructs the dependencies of the actual included transactions independently. This bounded-snapshot policy is an experimental departure from the draft's unconditional whole-active-pool wording.

## Header and Engine transport

The header appends the RLP `recursive_stark` pair after the Bogota slot number. JSON represents it as `recursiveStark` with `starkProof` and `blockDepsHash`. Engine V4 payloads preserve the optional pair. The experimental SSZ extension appends the RLP-encoded pair as one variable byte field; payloads without the pair retain the existing V4 encoding. Compact database headers use an optional extension and preserve historical header bytes and flag widths.

The node workspace requires Rust 1.97.1 because the pinned native leanVM implementation requires it. This toolchain change, genesis activation key, transport capability, RPC method, SSZ extension, digest selection and resource policies are implementation decisions beyond the draft. A consensus client participating in this devnet must preserve this Engine extension. No consensus-client or FOCIL inclusion-list changes are included in these execution-client repositories.

Run this profile on an isolated devnet with matching execution and consensus configurations. The experimental genesis field does not add a finalized Ethereum hardfork or fork-ID schedule entry.

## Unsupported dependency scheme

`LEANSTARK_SCHEME` remains reserved and rejected, as required by the draft's frame validity rules. Recursive STARK aggregation of leanSPHINCS signatures is supported separately from user-submitted application STARK dependencies.
