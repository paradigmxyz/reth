Derek 6 hash-post-state attribution audit, 2026-09-04

The official target reports hash-post-state named-worker duration decreasing from 0.31 to 0.27 ms (-12.93%, reported 95% half-width 4.83 percentage points). Overall payload latency and throughput remain neutral, and persistence wait decreases 3.05%, below the 5% qualification floor. This is a comparison of original baseline eadb887f against combined candidate a0d8b420, not an isolated comparison of packed-key sorting against retained33.

The worker metric is elapsed task time, not thread CPU time. WorkerMap starts its timer when the named worker runs the closure, separately records queue wait, and records task duration when the closure returns (crates/tasks/src/worker_map.rs:64–73,126–136). Any blocking inside the closure is included.

In the sparse strategy, the hash-post-state closure normally receives already hashed state through a channel (crates/engine/tree/src/tree/payload_validator.rs:760–770). The sparse strategy supplies that receiver (state_root_strategy/mod.rs:878–889); its event loop sends the accumulated final_hashed_state when it consumes FinishedStateUpdates (state_root_strategy/sparse_trie.rs:458–464). The named worker's fallback hashes BundleState addresses and storage keys only if that receiver is absent or fails; HashedPostState::from_bundle_state collects maps and does not call the changed sparse-trie leaf sort (crates/trie/common/src/hashed_state.rs:46–69).

The changed B256 sort is in ArenaSparseTrie::update_leaves (crates/trie/sparse/src/arena/mod.rs:2597–2600). The sparse task calls it separately for each storage trie and for the account trie (state_root_strategy/sparse_trie.rs:620–683). Its event loop alternates received updates/proofs with make_progress before it can consume the finish marker (same file:271–303). Faster leaf updates can therefore make the final hashed state available sooner, indirectly shortening the named worker's receive wait. This mechanism is plausible from source, but the reported worker duration does not establish faster hashing CPU or directly measure sorting. Scheduling, proof availability, and the other retained candidate changes may also affect it.

Batch-size coverage

The actual update_leaves input length is a trace-span field named num_updates (arena/mod.rs:2582–2588), not an exported histogram. SparseTrieTaskMetrics exports duration histograms for process_updates/reveal/final updates and aggregate account/storage cache-hit/miss histograms, recorded once per completed task (sparse_trie.rs:366–369,973–1016). Hits/misses count offered updates across passes, including touched entries and retries; process_updates calls can cover many storage tries plus the account trie. Dividing these aggregate counters by process_updates calls does not reconstruct the batch-size distribution seen by individual sorts.

The complete feature-1 target-metrics-scrapes.jsonl inventory contains 28 metric names, consisting of selected duration sums, canonical height, and transaction counters; it does not contain actual update/reveal batch sizes. The companion raw-metric phase audit can quantify process/reveal call frequencies and cumulative cache workload, but a claim that real sorting batches are smaller than the kernel fixtures needs trace fields or direct per-sort-size instrumentation. No new production instrumentation or source changes were made for this audit, and no full raw-data scan was duplicated.
